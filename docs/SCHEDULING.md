# 调度、容量备用与限额

正常调度选择账号，容量备用处理符合条件的失败，两者保留各自的范围。Dynamic fallback is bounded, process-local, and only applies where replay is safe.

## 正常账号选择

请求先经过平台 Key 的状态、模型、账号分组、套餐和额度等约束，再按既有调度与会话绑定选取账号。后台可选择 `ordered` 或 `balanced`；`balanced` 按 Key 与模型轮转候选，并保留线程分配和会话绑定。新增动态备用不会把所有首选请求都改成“最低负载优先”。

源码在没有持久化设置或环境覆盖时回落为 `ordered`；需要均衡轮转的新部署应在后台明确选择 `balanced`。迁移部署使用已有持久化配置，不自动重置策略。

网关只知道经过自身进程的在途请求，无法看到同一上游账号绕过网关的客户端直连流量。账号越多也不代表所有模型容量或额度线性增加。

## 动态容量备用

启用 `CODEXMANAGER_DYNAMIC_OVERLOAD_ENABLED` 后，HTTP Responses 生成请求遇到可安全重放的结构化 `server_is_overloaded`，会取消失败流、记录账号与实际模型的容量冷却、释放旧占位，再经短暂抖动退避选择一个备用。

选择时重新检查当前 Key 授权、账号状态、模型/套餐、额度和冷却，在合格账号中按本进程观测的账号总在途数选取并原子预占。预占但尚未发送也计入在途；负载相同时按池与模型轮转。默认等权，不用未经校准的首字延迟或额度百分比推算账号能力。

Chat Completions 经 Responses 适配的流式与非流式请求也覆盖。没有可用候选或预算时保留原始容量错误，不遍历整个账号池。

## 重放和预算

- 一次容量故障最多使用一个实际备用，备用最多发送一次生成请求。
- 启用该动态账本时，一次逻辑请求最多三次物理生成发送，包含原账号的传输或认证重发。
- 每个池与实际模型有共享预算：初始及容量均为 3 次；首次生成补充 0.2，每次额外发送消耗 1。备用先预留，未实际发送则归还。
- 所有尝试沿用原请求总截止时间，不为备用重新开始计时。

一旦上游产生内容、推理或工具调用，或请求含有账号绑定的服务端历史、文件、加密/压缩内容或托管工具，不透明重放。即使无法重放，已经识别的结构化容量错误仍会更新健康状态。

HTTP 200 响应头不等于成功。健康成功及会话迁移要求观察到成功语义终态和完整客户端交付；会话迁移通过旧账号与 epoch 条件更新，避免并发覆盖。明确的客户端断连且未观察到实际 upstream 错误时，不因缺少结束事件惩罚整个账号；请求仍记录交付失败，也不会建立成功绑定。

## 冷却和恢复

容量冷却按账号与实际模型区分，采用 30、60、120 秒退避和 ±20% 抖动，并考虑有效 Retry-After。冷却到期后只放行一个真实请求试探；语义成功后进入最多 2 并发的恢复阶段，至少稳定 30 秒且再完成 3 次成功才解除恢复限制。配置的账号总并发更低时使用更严格的限制。健康稳定 5 分钟且满足成功条件后才清除退避级数，旧代际成功不能解除新故障。

对 Content-Type 缺失或误标的流，识别在既有 64 KiB / 10 秒预读边界内进行；普通文本、JSON、未知格式及已经输出的内容不会任意改写。旧 HTTP 429/503 的部分提前返回路径仍保留账号级处理，不能把所有错误都理解为新增模型级熔断。

## WebSocket 与状态边界

直接客户端 WebSocket 会话以及 `/v1/responses/compact` 不进入新增的动态备用选择，保留既有重连和上下文恢复路径。HTTP 请求内部转为上游 WebSocket 时，其实际生成发送仍受这个 HTTP 请求的账本约束。原生 WebSocket 会话绑定也在成功终态完成交付之后写入。

健康、账号在途计数与共享重试预算均为**单进程内存状态**。重启后未知账号/模型先单请求试探再渐进恢复，池预算也重新建立；跨重启不存在累计“20% + 3”的保证。多实例没有共享调度协调，不能将本策略直接视为分布式限流器。容量电路和池各有 10,000 项上限，定期清理闲置 24 小时状态，并保护仍在使用的占位与预算。

## 账号并发、Key 限额和队列

`CODEXMANAGER_ACCOUNT_MAX_INFLIGHT` 或后台相应设置控制账号总在途上限；源码默认 `0` 表示不额外设置该硬上限，动态探测与恢复限制仍独立生效。它不是每个账号可单独配置不同权重或不同并发值的调度系统。

现有请求门以 Key、请求路径和模型为粒度尝试串行执行对应路径；门等待超时或锁异常时可以跳过该门继续候选流程，仍受请求总截止时间检查，因此它不是每个 Key 的硬并发限额。工作线程及队列另有各自限制，当前也不提供一套可自定义每个 Key 并发数、RPM 和 TPM 的通用限流配置。等待时间、总截止时间和客户端超时会共同影响请求结果。

平台 Key 可配置累计 Token 上限，认证时会比较已经记录的用量，达到上限后拒绝后续请求。该检查不是对未来输出 Token 的精确预扣，正在执行或同时进入的请求可能使最终用量超过阈值。上游订阅额度、平台 Key Token 累计和估算费用是不同统计口径，不提供固定比例均分或精确互换保证。

模板通过 `DYNAMIC_OVERLOAD_ENABLED=true` 显式启用动态路径；源码开关默认关闭且仅在启动时读取。调整后重启服务。配置方式见 [配置参考](CONFIGURATION.md)。
